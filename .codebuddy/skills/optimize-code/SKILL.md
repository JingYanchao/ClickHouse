# ClickHouse Code Optimization Skill

## Arguments

- `$0` (required): Branch name, diff spec (e.g., `my-feature-branch`, `HEAD~3..HEAD`), or file path(s)

## Phase 1: Obtain Target Code

**If a branch name is given:**
- Get the diff against master: `git diff master...$0`
- Get the changed file list: `git diff --name-only master...$0`

**If a diff spec is given (e.g., `HEAD~3..HEAD`):**
- Get the diff: `git diff $0`
- Get the changed file list: `git diff --name-only $0`
- Get commit messages: `git log --oneline $0`

**If file path(s) are given:**
- Read the file(s) directly
- Use `git diff HEAD -- <file>` to see uncommitted changes if any

For each target file, read the **full file content** (not just the diff) — optimization requires understanding the complete context.

If the target is very large (>5000 lines across all files), use the Task tool with `subagent_type=Explore` to analyze different parts in parallel.

## Phase 2: Style Compliance Check (ci/jobs/scripts/check_style)

Run the ClickHouse style checks against the target files. These rules come from `ci/jobs/scripts/check_style/` and **must be enforced**:

### 2.1 C++ Style Rules (from check_cpp.sh)

Check and auto-fix the following violations:

**Brace style (Allman style required):**
- Opening `{` must be on a **new line** after `class`, `struct`, `namespace`, `enum`, `if`, `for`, `while`, `else`, `throw`, `switch`, and after `)` (including `const`/`override`).
- **Auto-fix**: move `{` to a new line.

**Whitespace rules:**
- No trailing whitespace.
- Indentation must be multiples of 4 spaces; no tabs.
- A space is required between keywords (`if`, `for`, `while`, `catch`, `switch`) and the opening `(`.
- No whitespace immediately inside parentheses: `( x )` → `(x)`.
- No three or more consecutive empty lines.
- No whitespace before comma: `x , y` → `x, y`.

**Forbidden patterns:**
- `std::stringstream` / `std::istringstream` / `std::ostringstream` → Use `WriteBufferFromOwnString` or `ReadBufferFromString`.
- `std::regex` → Use `re2`.
- `std::mt19937` / `std::random_device` → Use `pcg64_fast` from `pcg_random.h` and `randomSeed` from `Common/randomSeed.h`.
- `std::shared_mutex` → Use `DB::SharedMutex`.
- `std::format` → Use `fmt::format`.
- `std::filesystem::is_symlink` / `std::filesystem::read_symlink` → Use `DB::FS::isSymlink` / `DB::FS::readSymlink`.
- `__builtin_unreachable()` → Use `UNREACHABLE()` from `defines.h`.
- `magic_enum.hpp` → Use `<base/EnumReflection.h>`.
- `hardware_destructive_interference_size` / `hardware_constructive_interference_size` → Use `CH_CACHE_LINE_SIZE` from `Common/CacheLine.h`.
- Quotes for includes (`#include "..."`) → Use angle brackets (`#include <...>`), except for autogenerated files (`config.h`, `config_tools.h`, etc.).
- `std::cerr` / `std::cout` in `src/` (with known exceptions).

**Naming conventions:**
- Abbreviations must be all-caps: `SQL` not `Sql`, `HTTP` not `Http`, `XML` not `Xml`, `JSON` not `Json`, `CPU` not `Cpu`, etc.
- `LOGICAL_ERROR` exception messages should not include "Logical error" text (it gets printed twice).

**Header hygiene:**
- Every `.h` file must start with `#pragma once`.
- No `// namespace` closing comments (they are unneeded).
- Avoid including `Interpreters/Context.h` in `.h` files; use `Context_fwd.h` instead.
- Avoid including `Core/Settings.h` or `MergeTreeSettings.h` in `.h` files; use forward declarations.
- Non-trivial function bodies should be in `.cpp` files, not headers.

**ErrorCodes / ProfileEvents / CurrentMetrics:**
- Each `extern const` declaration must be used in the same file.
- Each usage like `ErrorCodes::XXX` must have a corresponding `extern const` declaration in the file.
- No duplicate declarations.

### 2.2 Various Checks (from various_checks.sh)

- No executable bit on non-executable files (`.cpp`, `.h`, `.sql`, etc.).
- No BOM markers (UTF-8, UTF-16).
- No conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`).
- No DOS/Windows newlines (`\r\n`).
- No Cyrillic characters mixed into Latin text.
- No orphaned header files (`.h` without any `.cpp` including it).
- No `#ifdef NDEBUG` (likely meant `#ifndef NDEBUG`).
- Unsafe `dynamic_cast<T*>(x)->` patterns — use references or nullptr check.
- `close(fd)` return value must be checked.

### 2.3 Settings Style (from check-settings-style)

- Settings declared with `DECLARE(...)` must have consistent types across all declaration files.
- No duplicate `extern` declarations for settings.
- Every `extern const ...Settings` usage must have a corresponding declaration.
- Avoid including `Settings.h` / `MergeTreeSettings.h` in `.h` files.

## Phase 3: Code Structure Optimization

After fixing style violations, analyze and optimize the code structure:

### 3.1 Function/Class Organization
- **Long functions**: Break functions exceeding ~80 lines into smaller, well-named helper functions.
- **Deep nesting**: Flatten `if/else` chains using early returns, guard clauses, or extracting into helper functions.
- **Code duplication**: Identify and refactor duplicated logic into shared functions or templates.
- **God classes**: Identify classes doing too much; suggest splitting into focused, single-responsibility classes.

### 3.2 Resource Management
- Replace raw `new`/`delete` with RAII types (`std::unique_ptr`, `std::shared_ptr`, or ClickHouse-specific wrappers).
- Ensure file descriptors, sockets, and other resources are properly closed on all paths (including error/exception paths).
- Prefer stack allocation over heap allocation when lifetime is local.

### 3.3 Performance Patterns
- Move expensive computations out of loops.
- Use `reserve()` for vectors when size is known or estimable.
- Avoid unnecessary copies; prefer `const &`, `std::move`, or `std::string_view` where appropriate.
- Replace `std::map`/`std::set` with `std::unordered_map`/`std::unordered_set` (or ClickHouse `HashMap`) when ordering is not needed.
- Use `if constexpr` to eliminate dead template branches.

### 3.4 Error Handling
- Ensure all error paths are covered (no silently ignored return values).
- Prefer specific exception types over generic ones.
- Check that error messages are clear, actionable, and include enough context for debugging.

### 3.5 Header Dependency Reduction
- Move function bodies from `.h` to `.cpp` where possible.
- Replace `#include` with forward declarations where full definition is not needed.
- Use `_fwd.h` headers for widely-used types.

## Phase 4: Auto-fix and Report

### 4.1 Auto-fix (Apply directly)
Apply fixes **directly** to the source files for the following categories:
- All style compliance violations from Phase 2 (brace style, whitespace, forbidden patterns, naming, header hygiene).
- Simple structure improvements (early returns, `reserve()` additions, `const &` fixes).
- **Simple bugs**: Bugs that have a clear, localized fix (e.g., off-by-one errors, missing null checks, wrong comparison operators, uninitialized variables, missing `break` in `switch`). These should be fixed directly with a brief inline comment explaining the fix.

When making fixes, preserve the original logic and semantics. If unsure about the fix scope or impact, do NOT auto-fix — report it as a discussion item instead.

**Criteria for "simple bug" auto-fix:**
- The fix is ≤ 5 lines of change.
- The fix is localized to one function or one logical block.
- The intent and correctness of the fix are unambiguous.
- No behavioral/API change is introduced.

### 4.2 Complex Bug & Discussion Report

Output the following sections for human review:

**🔴 Complex Bugs Found (Needs Discussion)**
Bugs that require larger refactoring, cross-file changes, or design decisions:
- `[File:Line(s)]` Description of the bug
- Explanation of the impact
- Why it cannot be auto-fixed (scope too large, multiple valid approaches, behavioral change, etc.)
- Suggested fix approach (code snippet or refactoring strategy)

**🟡 Structure Issues (Recommend Fix)**
Non-trivial structural improvements that need human judgment:
- `[File:Line(s)]` Description of the issue
- Why it matters (maintainability, performance, readability)
- Suggested refactoring approach

**🟢 Auto-fixes Applied**
Summary of all auto-applied fixes:
- Style fixes: count of each fix type (e.g., "Fixed 5 trailing whitespace, 2 brace style, 1 forbidden pattern")
- Simple bug fixes: list each bug fixed with `[File:Line]` and one-line description
- List of files modified

## Execution Strategy

1. Read all target files completely.
2. Run style checks first (fastest, most mechanical).
3. Apply style auto-fixes.
4. Analyze structure and identify optimization opportunities.
5. Apply safe structure fixes.
6. Identify and auto-fix simple bugs (localized, unambiguous, ≤5 lines).
7. Collect complex bugs and discussion items.
8. Output the report.

For large changesets, use Task tool with `subagent_type=Explore` to parallelize:
- One subagent per subsystem (e.g., storage, query execution, coordination).
- Each subagent focuses on its area and returns findings.
- Main agent aggregates and deduplicates results.

## Examples

- `/optimizeCode my-feature-branch` — Optimize changes on branch vs master
- `/optimizeCode HEAD~3..HEAD` — Optimize the last 3 commits
- `/optimizeCode src/Storages/MergeTree/MergeTreeData.cpp` — Optimize a specific file
- `/optimizeCode src/Storages/MergeTree/` — Optimize all files in a directory

## Notes

- Style fixes are applied automatically; structural changes and bugs are reported for discussion.
- The skill respects ClickHouse's existing code style and CI check rules.
- All fixes preserve backward compatibility and existing semantics.
- When in doubt, report rather than auto-fix.
